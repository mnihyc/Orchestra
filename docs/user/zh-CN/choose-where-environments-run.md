# 选择环境运行的位置

每个环境有两个名称：它**运行于**什么之上（Docker 或一台机器），以及它的**运行时**，即把它圈住的程序。两者并排显示，例如 **Docker · gVisor**。运行时按其原名显示，并附一句话说明它与主机共享什么：

- **runc**：与主机共享内核。
- **gVisor**：自带的内核，用用户态写成。
- **Kata**：微虚拟机，有自己的内核。

主机登记的其他运行时（crun、Sysbox）以各自的名称显示。Docker 无法得知一个运行时是什么，所以由运维人员在节点配置中声明；没有人声明过的运行时，视为与主机共享内核。

## 创建环境时选择运行时

打开**资源 → 环境 → 添加环境**。模板给出起始的运行时；**运行时**选项列出所选主机提供的运行时。模板不允许、或位置禁止的运行时会连同原因一并显示。位置若要求某一个运行时，它就是唯一可选的。专家可在**其他运行时名称…**下输入主机已登记的名称。

模板在**限制 → 运行时**中给出默认运行时，也可限制可选范围。位置的策略（`environments.runtimes`）可允许、禁止或要求某些运行时，并可像其他策略一样锁定。

**运行时**留空时使用主机的默认运行时，它同样必须符合模板和位置的规则。同一运行时登记的别名遵循相同规则。Orch 会在创建运行单元前再次检查策略；规则改变可能阻止正在进行的创建或替换。

环境页显示它的组合、那句共享说明，以及**此处的限制**：在它的运行时下哪些事情做法不同，写成“怎么做”与“为什么”。同样的内容会在每次会话开始时告诉智能体，环境迁移或运行时变化之后也会再告知。

如果主机在拉取或构建镜像时空间不足，请在该主机释放空间后重试。磁盘已满时，Orch 不会改用旧的缓存镜像。

## 有哪些组合

| 运行于 ＼ 运行时 | 无 | runc | gVisor | Kata |
|---|---|---|---|---|
| **机器** | 唯一的选择 | — | — | — |
| **Docker** | — | 默认 | 登记了 `runsc` 时 | 登记了 Kata 且有 `/dev/kvm` 时（虚拟机上需嵌套虚拟化） |

## 每种组合支持什么

| | 机器 | runc | gVisor | Kata |
|---|---|---|---|---|
| 边界 | 无 | 共享内核 | 用户态内核 | 独立内核 |
| 工作区、主目录、状态 | 目录 | 存储卷 | 存储卷 | 存储卷（virtio-fs） |
| 终端、文件、MCP、执行器、浏览器、端口 | ✓ | ✓ | ✓ | ✓ |
| 共享和只读挂载 | ✓ 原地 | ✓ | ✓ | ✓（virtio-fs，元数据较慢） |
| 对外部所做更改的文件事件 | ✓ | ✓ | 重新扫描（约 1 秒） | 重新扫描（约 1 秒） |
| 不换新单元即可更改挂载或设备 | ✓ | ✓ | 环境重建 | 环境重建 |
| 受限网络 | — | ✓ | ✓ 在主机上证明可行时 | ✓ 在主机上证明可行时 |
| 主机网络 | ✓ | 需能力 | ✗ | ✗ |
| 内置 Docker（`docker_inside`） | ✓ 原生 | ✗（只有高风险的 `privileged` 和 `docker_socket`） | ✓ 没有可供 Docker 自身网络使用的防火墙：在内部启动的容器请用 `--network=host` 访问网络（`-p` 仍可提供端口） | ✓ |
| `sudo` 等 set-user-ID 程序 | ✓ | ✓ | 仅当 `runsc` 以 `--allow-suid` 登记时（`gvisor.sh` 会设置） | ✓ |
| 内部运行虚拟机（QEMU） | ✓ KVM | ✓ 需 `kvm` 能力的 KVM | 仅软件模拟 | 仅软件模拟 |
| GPU | ✓ | 需能力 | ✗ | ✗ |
| 存储卷之外安装的软件在停止、空闲停止、回收和重启后保留 | ✓ | ✓ | 仅在 `--overlay2=none` 时（可选的 `gvisor.sh` 会设置） | ✓ |
| 同镜像替换时把这些软件作为保留层带走 | ✓ | ✓ | 仅在 `--overlay2=none` 时 | ✓ |
| 主机在单元上限之外多花的内存 | 无 | 无 | 数十 MiB | 约 0.3 GiB |
| 主机准备 | 无 | 无 | 安装并登记 `runsc` | 安装并登记 Kata；需 KVM |

某种组合没有的能力，会在本应提供它的地方连同原因显示：例如在 Kata 下不提供**主机网络**，因为客户机有自己的网络。

## 安装的软件何时丢失

用 `apt`（或手工）装在存储卷之外的软件，存放在单元自己的文件系统里。**停止**、**空闲停止**、**回收**和**重启**是否保留它，按表所示。单元会在以下情况被**替换**：重新创建、更新、模板变更、无法即时应用的配置或能力变更（gVisor 或 Kata 下的每次挂载或设备变更，以及**内置 Docker** 本身）、替换出错的单元，以及迁移。运行时允许时，同镜像的替换会把它作为保留层带走；换了镜像则从头开始。计划和授权对话框会说明适用哪一种：“自环境创建以来在存储卷之外安装的软件（例如用 apt 安装的）会被移除。镜像自带的软件和存储卷保持不变。”各个存储卷，包括 `/var/lib/docker`，始终保留。

迁移和恢复计划无法携带旧托管环境的保留镜像时，会显示软件移除提醒。携带镜像的计划会保留其中的软件，即使测量大小为零。从机器目录迁移不会移除安装在该机器上的软件。

在 gVisor 的默认叠加层下，环境每次停止都会丢失软件：“在存储卷之外安装的软件会在环境停止时丢失；请把它放进镜像或存储卷。”可选脚本 `deploy/hosts/runtimes/gvisor.sh` 用 `--overlay2=none` 登记 runsc，使它像 runc 一样保留软件；见运维页面“推荐的主机配置”。

## 内置 Docker 与开发者工具模板

**内置 Docker**是一项能力，只在拥有独立内核的运行时（Kata、gVisor）下提供，风险为中等：它给予全部内核能力并撤去容器的过滤，只在客户机内部。Docker 把数据放在 `/var/lib/docker`，Orch 在环境每次启动时把它做成环境状态存储卷的一处挂载：Kata 下是卷中一个文件里自带的文件系统，gVisor 下是卷中的一个目录。在与主机共享内核的运行时下，只能通过主机的套接字或特权模式使用 Docker，两者都是高风险，默认拒绝。

先申请内置 Docker，再安装 Docker：授予它会使环境重建。**开发者工具**模板用的镜像已内置 Docker Engine（含 buildx 和 compose）、x86_64 与 aarch64 的 QEMU 以及常用构建工具；在那里用 `orch-dockerd` 启动 Docker。在默认环境中，智能体可以自己用 `sudo apt-get install docker.io` 安装 Docker 并启动 `dockerd`。没有 Docker 的镜像会在申请内置 Docker 的地方说明：“此镜像未安装 Docker：可用 sudo 安装（在环境重建前一直有效），或从内置 Docker 的“开发者工具”模板创建环境。”

如果内部服务在本地可以访问，但其他机器无法访问其发布的端口，请检查内层 Docker 的桥接子网是否与主机或客户端网络重叠。在环境内的 `/etc/docker/daemon.json` 中设置不重叠的 `bip`，然后重启内层守护进程。

启动失败时请查看 `/var/log/dockerd.log`：辅助程序总共最多等待一分钟，且仅在启动进程退出后重试一次。

Orch 会在主机上可用的镜像中检查 Docker 客户端、守护进程和两种 QEMU 系统程序，无论镜像是拉取、构建、导入还是已缓存。检查只确认程序是否存在，不启动这些程序。无法检查镜像时，可用性保持未知；检查失败不代表程序缺失。

在 Kata 或 gVisor 环境内部运行的虚拟机靠软件模拟：能用，但慢。在普通容器上，`kvm` 能力可使其变快，代价是容器持有主机 `/dev/kvm` 带来的较弱隔离。
