# 更新 Orch 和机器

机器或节点会把它的**运行版本**与自己的 Orch 服务器推荐的构建比较。列表里的**有可用更新**标出较新的推荐，页面会写出两个版本。已下载的文件不会被报告为运行版本。这要等新进程重新连接后才会改变。本页说明如何更新机器或节点、机器可以拒绝什么、环境和托管提供方如何更新，以及服务器本身如何更新。

## 机器和节点

拥有**机器管理**权限的人，或对节点拥有**主机管理**权限的人，可以在它的页面或它所在行的操作里选择**立即更新**。

1. Orch 暂停新的轮次，等到使用这台机器的每个运行中轮次结束。对节点来说，这包括它所承载的每个容器里的轮次。
2. 程序从它自己的服务器下载适合它平台的构建，检查它的大小和 SHA-256，并一步替换可执行文件。
3. 服务管理器启动新的程序。这不会中断已有的轮次。

请求在等待、下载、安装和重新连接期间，这一行会写着**更新中…**。新进程报告它的版本之后，它就会清除。被拒绝或失败的更新会把原因保留在这一行和页面上。损坏的下载会让运行中的程序保持原样。请求会记录在审计里，自动的请求也一样。

只要自动更新的设置允许，机器上的连接器和节点也会在它们每小时的检查中自己请求推荐的构建。它们使用与按钮相同的等待、验证和安装。环境或托管提供方内部的连接器不会替换它自己。

## 本机策略拒绝时

机器主人用 `update.auto` 控制自动更新。关闭自动更新时仍可选择立即更新，而且这次操作不会开启自动更新。运维也可以在本机明确请求同样经过验证的更新：

```sh
orch-connector update
orch-node update
```

只运行本机对应程序的命令，保存的 `update.auto` 值保持不变。低于服务器最低接受版本时，已通过身份验证的程序无需先建立普通连接，就能取得空闲后的更新许可。服务器会先暂停新轮次，等待使用该机器的全部工作结束，其中包括所有受管单元。因其他原因离线的机器仍须先恢复到服务器的网络连接。不能因节点自己没有程序会话就推断单元空闲。协议不再兼容时，由运维在该机器上执行本地更新命令。

低于服务器接受的最低构建时，需要先更新才能恢复正常工作。在服务器等到它承载的每一轮都结束之后，节点可以在它通常的连接被拒绝的情况下得到这个更新。它绝不会把空的本地智能体程序列表当作它的容器处于空闲。如果程序不再有共同的链路协议，运维人员请在主机上使用 `orch-node update`。

## 环境和托管提供方

环境保留它自己的**更新**流程。它事先的检查会显示待处理的镜像、连接器和其他更改，以及阻止替换的运行中的工作。环境的管理者审阅这个方案并开始它的作业。更新主机的节点不会悄悄替换容器的镜像或连接器。托管提供方同样通过它的容器的更新，或在它下一次启动时，取得它的连接器。目录的连接器属于它的机器，遵循那台机器的策略。

## 服务器

**管理 → 系统**显示正在运行的服务器的版本、从运维人员的发布地址读取的最新发布版本、指向它的说明的链接，以及要在服务器的主机上运行的确切命令，例如：

```sh
./update.sh v1.2.3
```

默认的地址是这个项目的 GitHub 发布页。运维人员可以在 `config/orch.toml` 里设置 `[release] url`，或设置 `ORCH_RELEASE_URL`，来使用另一个兼容的发布来源。服务器至少缓存读取结果一小时，包括失败的查询。定期的通知仍由 `release.check_days` 控制，打开**系统**读取的是同一个每小时的缓存。如果查询失败，会把原因连同最后一次成功的结果及其日期一起显示在旁边。如果已有检查正在进行，点击**立即检查**会显示提示，并保留上次可用的版本。稍后可再次查看结果。

服务器在网页上没有安装它自己的更新的按钮，因为那需要对主机文件或它的 Docker 套接字的权限。运维人员在那台主机上运行命令 `update.sh`。它作为一个事务运行：验证发布版本、备份数据库，并在新的服务没有就绪时回滚。运维指南的“更新和回滚”涵盖了备份和回滚。

API 更新它的数据库期间，网页入口保持可用。已打开的页面会显示正在进行的迁移、已完成的步骤、数据库可以报告的任何行数，以及已用的时间，然后在服务器就绪时重新连接。同样的步骤会打印在 API 的更新日志里。数据库无法报告时，计数保持未知。
