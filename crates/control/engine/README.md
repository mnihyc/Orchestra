# orch-engine


A host's provider-unit removal reuses the provider cleanup phases: stop, remove the exact unit,
optionally delete unshared owned volumes, then revoke that unit's connector. Its saved volume choice
survives reaper retries. The provider remains, so its next turn provisions a new unit; an older kept
unit's removal leaves the current unit attached. `tests/provider_runtime.rs` covers these paths and
the rollback of a refusal while a turn runs. These regression sources are authored, unrun.

`tests/provider_homes.rs` covers borrowed harness-home provisioning and recreate, the explicit
cross-host copy offer, whole-home import before destination creation, and preservation of originals.

Durable product orchestration hosted inside the API.

Runtime change observations compare the frozen semantic definition. Object key order (including a
PostgreSQL jsonb round trip) and tool catalogue order do not make a fresh unit Behind; actual build,
resource and ordered-command changes still do. Older units use their frozen definition/builds when
available rather than an order-sensitive legacy hash. `tests/updates.rs` covers both preflight and the
batched page observation, catalogue/object reorder, genuine build/resource changes and argv order.
Source authored; the integrator runs its proof with the complete round.

Creating units, active environment replacements/moves and accepted removals do not emit another
pending-update assessment while their lifecycle is in progress. A verified, stable unit still reports
real desired-definition changes. The fresh-unit integration proof reads both sides of enrollment.

A completed turn stays quiet for its own input author while that thread is visible on an authorized
live connection. The existing realtime sink supplies merged reader presence synchronously, without
outside I/O during the transaction. An absent realtime side retains normal delivery. Away authors,
other followers, failures and node destinations are unchanged. Notifications and realtime API tests
cover the suppression, ordinary delivery and cross-process/tab presence.

Pending inputs keep their identity and author when delivery changes through the ordinary
input PATCH. Drivers choose queue (last), steer (into a supported running turn, otherwise
first with no running turn) or interrupt (stop the active turn and go first); an unsupported
live steer refuses with the interrupt alternative. Authors alone edit words or native
selections. A delivery change or reorder never lifts a Stop, cap or file hold. Queue
mutations advance the revision and state stamp, so sync and live readers see the updated
input and a stale resume cannot release a queue changed since it was read. HTTP and socket
regression sources are in the API's `tests/threads_drive.rs` and `tests/realtime_threads.rs`.

Environment moves use one reviewed plan and job for declared unit and directory lifecycles. They
check ordinary destination Use authority and live machine policy, reserve a fresh owned-data
generation, carry the recorded-state store even when home copying is off, and verify its dependencies
before publishing the destination. An existing directory needs explicit copy consent and stays
untouched; detached source-directory data remains a recovery copy. A legacy native home is included
only when selected. `tests/machine_moves.rs` and `tests/source_uniform.rs` contain the cross-machine
and repository-default regressions; these additions await the integrator's execution.

Initial source preparation belongs to the provisioning job's enrolled runtime, before the environment
publishes its running identity. Attachment, native file-state storage and source work use that runtime's
generation; the final commit publishes it once. Only the exact open owning provisioning job may use
this pending target, with ordinary resource/write policy checks and a final identity check before
source publication. Standalone file jobs require the published identity. `tests/provisioned_source.rs`
covers empty and repository-backed temporary workspaces, the held file command before running, the
original first input afterward, and machine/generation changes before the file reply. The source
publication reuses its already locked job row rather than acquiring another pool connection.

Archive and deletion settle turns, queued inputs, approvals, leases and sessions in one transaction with replayable controls. Environment cleanup freezes owned volume references and retention, resumes after restart, and leaves successor volumes in use alone; database and Docker integration tests exercise these paths.

Native recording publication may outlive the environment's capture key, but a
turn still waits for its own verified manifest and durable command answer. An
expired answer cannot become a complete before-state. Leased cleanup jobs retry
only retryable `busy` for detach, owned-data removal and destructive data import,
using derived command identities, the same frozen body and the original deadline;
exhaustion leaves an explicit job failure. Committed withdrawals of directory
registrations also checkpoint and retry Busy detach controls durably while the
same registration remains withdrawn, within that original deadline. No database
transaction waits on a machine, content transfer or retry timer. Recording cleanup,
temporary-environment and source regression sources cover these paths.

Recovering a cleanup phase first replays retained terminal outcomes and follows
retained Busy retry identities. It applies neither another retry delay nor a new
deadline to an already successful command. The original deadline still bounds
new or unfinished attempts. Recovery sources reconstruct an uncommitted phase
checkpoint after native durable success, restart beyond that deadline and require
both original-command and Busy-child success with no further native execution.

Restored threads stay archived, and unarchiving alone starts no turn. A new input can resume their native conversation when the binding and harness support it.

Delivered input distinguishes Orch notices from relayed words, breaks reserved marks in authored content and keeps the original stored text. Announcements accept at most 1,500 characters, document tools use `seq`, and downloads use `save_to`; database-backed delivery and tool cases cover these paths.

Internal tool failures, including database acquisition and query errors, return the safe `unavailable` refusal through the ordinary result command. A closed-pool regression keeps the native transport available, requires that refusal within the normal test bound, and preserves one protected answer on replay.

Runs durable threads, resource workflows and managed runtime jobs inside the API. Updates and recreations hold affected threads, keep persistent data and restore the previous unit on failure; workspace moves for separated threads and idle recycling use the same lifecycle checks. Database integration tests, scripted machines and a real Docker persistence test cover these operations.

Harness approval news is queued on the unit's database connection and delivered at commit, including
native report transactions. A turn keeps completed human-wait milliseconds and its open wait boundary;
overlapping requests pause once, and a withdrawal or terminal turn closes the interval. The API socket
tests exercise both decisions and answers across two API processes. Conversation search strips reserved
injected context before masking and truncation. Startup repairs only old context-bearing projections in
bounded independent transactions; the search query withholds those old projections until repaired.

Before-state metadata recovery uses only a retained successful recording and its original protected
request. It shares normal capture's manifest/root/generation checks, preserves the original expiry and
pins, and never issues a recording command. A store fallback with no valid original remains unavailable;
another generation and expired or explicitly unavailable native captures are never reconstructed.

Removal freezes its kept-file window and owned references. Restore reuses provisioning on the original volumes and returns a verified stopped generation without source preparation, init or a model call; purge records physical confirmation and preserves a failed promise. Production approval, interruption, cancellation and verified provisioning facts are audited. Native file observation awaits Ksource, restricted-network restoration awaits Kegress, and connected registrations, private-view layout and failed rollback recovery are not complete.

Search projections keep masked conversation text as items arrive, omit side threads, and rebuild conversation, chat and document text from their current sources. Finder candidates are checked in bulk for nodes, documents, chat participation and resources; live writes, repair and privacy are tested on a real database.

The core of the thread engine is built and tested: an input that is accepted becomes exactly one turn, what a harness says is applied exactly once and in order, and nothing is let through a check that could not be made. It runs inside the API (`orch-api-core` builds it at start, sends its commands through the link's dispatcher and registers it as the applier of what machines say) and is tested on a real database with a scripted machine standing for a connector with a harness (`tests/`).

Harnesses report their real descriptors during machine discovery before the first thread. Binding offers and selection use the same ordering and actual machine capabilities; key-separated placement keeps the harness with its environment and the credential with its provider, including fork previews.

A whole-project announcement, a person's or an agent's, goes to the open topics of the projects inside the project as well, and passes over a folder or a topic that was made private there (`tools/announce`, tested in `tests/folders.rs` and through the API).

The export of a place is built (`exports`, `export_layout`, `jobs/export`): what a person may read in an org, a project or folder, a topic or a thread is planned before anything is made (what an archive would hold, how large, what stands in its way, and what they read and may not take away, counted by the place it lies in and named only where they may know it), asked for as a job that streams a zip into the store of content a piece at a time (the memory it takes does not grow with the archive), listed, fetched by its person alone and removed. Each conversation, chat and document is read as its person at the moment it is written and goes in only where the Export row of that kind of thing is theirs, so what was lost between the plan and the writing is left out; a copy given to an agent and what `download_shared` copies into a workspace ask for the same row (`not_downloadable`), and a live share names the agents in the Export rows as far as whoever shares holds them. A link in a written form to one of its files is the path where the file lies beside the text, one rule (`written::files_beside`) for what an agent reads, a copy, a single export with its files and the archive of a place: `<title>.files/<name>` for a document (`../<title>.files/<name>` from an earlier version, which lies one directory below), `conversation.files/…` and `chat.files/…` where the text lies as `conversation.md` and `chat.md`, and in an archive the directory beside the file the text is kept in; the files an archive carries are those of inputs, of messages (what a forwarded message carried among them) and of documents, so that the files a step of a conversation left, which the text names at `full`, are not in it. They are tested on a real database in `tests/exports.rs` (the job, a role lost between the plan and the writing, a token's scopes, a job stopped or failed, how many may be written at once), `tests/exports_memory.rs` (a thousand things and large files, the peak of the process measured), `tests/sharing_export.rs` and `tests/shared_download.rs`; that a link in a document an agent reads leads to the file its tree lists is in `tests/shared_read.rs`, and that every link of an archive finds its file is in the API's `tests/exports.rs`.

What is built: `inputs` (queue, steer, interrupt, edit, cancel, drafts), `preflight` (each check in its order; the first that fails keeps the input waiting with its reason, and a question that cannot be answered lets nothing through), `turns` (the start sequence, steering, interrupt and the forced end of a turn that does not stop, presence), `sessions`, `harnesses`, `ingest` (every session event, applied once), `approvals` (the first decision wins, the harness is told once), `instructions`, `binding`, `leases`, `providers` (an API provider on a key), `models`, `rates`, `views` (a thread as readers are given it), and `caps`. Everything the engine remembers is in the database and changes by compare-and-set; commands carry identifiers derived from what they are for, and a supervisor looks at the database again and again, so a process built anew on the same database goes on where the last one stopped.

A turn that reaches a real model is built for an API provider on a key. The provider is started on the machine that holds its key (`provider.start`: the key goes as a reference to a secret, sealed to that machine when the command is written, or is not sent at all where that machine keeps it), when a turn needs it and it is not running; its standing and facts are kept from what that machine reports (`provider.status`, `provider.facts`), and it is stopped when it is switched off or deleted. A lease is opened on that machine before `turn.start` (`lease.open`, with the models the turn may use) and closed after the turn however it ended (`lease.close`); one whose turn is gone is closed by the supervisor. The session is opened on the forwarded path, with a ticket for the tunnel when the key is on another machine than the harness. Every use the forwarder reports (`lease.usage`) is one row of the usage ledger of `orch-db`, however many times it is reported, with the model, the tokens by kind, what the use ran on and the rate it was counted at (the provider's own, else the rate card, else the shipped catalogue marked as an estimate) and the credits that rate gives; a lease that is denied, or an upstream that refuses the key, is the turn's failure with its reason; and a model the provider does not enable, or the allowlist leaves out, keeps the thread waiting with that reason.

A request for access is an approval of its own kind: `approvals` makes one for each thing a person asks for, all with one batch, in the transaction that tells the nearest people who can give it; decides it as the approver's own change of the page together with the end of the approval, the audit row and the word to the person who asked (and once more when everything they asked for is held); and lets those nobody decided in time run out, from the supervisor; a person who already has as many batches waiting as the policy allows is told how many wait and what the most is, and an approver decides only what they could have given themself, which the card of the request says beforehand. The lines of a thing's history are read back by `history`: which kind of line in an environment's history an action is, which thread a line is about, and what it points at. They are tested in `tests/` of `orch-authz` and `orch-api-core` (`access_requests`), and in the unit tests of `history`.

A provider can be a person's machine. A profile whose harness never ran is not refused: the first time a caller who may use all that they chose asks for a thread on it, or for the switch of a thread without history to it, the harness is started once where the provider runs, else where the environment is, and what it declares is kept with the profile (`provider_setup`); the turn then finds it up and starts nothing. A subscription whose login its harness holds on the machine that also has the environment is the arrangement `together`: the turn starts the harness there on its own sign-in, with no key, no forwarder and no lease on any machine, and it is counted once, when it ends, from the totals its harness reported (a row of the usage ledger of origin `harness`; where a forwarder counts the requests, its rows are the counted ones). The machine that keeps a provider is asked to look at its credential (`provider.refresh`), and what it answers is kept as the provider's facts and moves its state; a harness is brought up anew, and the conversations it holds are listed, on the machines that run it (`harnesses`). What may be chosen for a thread, and a thread without history put on something else, are `binding`. They are tested with the scripted machine (`tests/together.rs`) and, from the API's tests, against the connector as a process.

**A provider that Orch looks after.** A subscription made through the API has a runtime of its own, a unit of the provider pool with one `state` volume that stays for as long as the provider does (`jobs/provider_provision` makes it, starts it and starts it again to renew a sign-in; `provider_runtime` starts it when a turn or a sign-in needs it and by hand, stops it by hand, which is refused while a turn runs on the provider unless the request says to interrupt it, and when it has been idle, and retires it with the provider so that a removal job takes it away). While the unit is not up the provider has no machine: pre-flight does not ask for one, and the start sequence of the turn starts the unit and waits for it, the thread saying that it waits for the provider; a unit that could not be made is not made again by every turn that comes. A sign-in is begun by one of the methods the profile's adapter declares (`provider_setup`): what a person gives for a secret field is sealed in a row of its own the moment the request has it, the command that gives it to the harness refers to the row, and the row goes when the command is over, when the unit could not be made, and after `[engine] login_pending_secs`; what the harness shows and asks is kept as it reports it, an answer goes back to it, a sign-in can be given up, and a harness can be signed out. A stopped unit is started so that its harness renews the sign-in it holds (queued by the worker), and a token whose end is known is told ahead to those who manage the provider. A harness that runs away from its provider can run on a copy of the credential or on the login itself (`credentials`): a copy is issued by the provider's runtime sealed to the machine of the harness under a lease that the start sequence opens once that machine is known, given to the harness before its session opens, written down each time it is issued, and replaced before it lapses or when the harness says it needs another (never more than once in thirty seconds); the login is taken for one environment at a time by a compare-and-set in the transaction that starts the turn, delivered to the harness there, and brought home when a person asks, when the environment stops, moves or goes, or when no thread there needs it any longer, by the environment giving it back sealed to the provider's runtime and the runtime taking it; a return that fails leaves the credential where it is, keeps what was given back sealed for the next try, and can be given up, which puts the provider in `needs_setup`. They are tested with scripted machines and a scripted host (`tests/provider_runtime.rs`, `tests/provider_sign_in.rs`, `tests/credentials.rs`).

Environments made from templates are built too (`places`, `environments`, `hosting`, `reports`, `reaper` and the jobs `runner`, `provision`, `health` and `remove`). Where an environment could be made is worked out from the hosts its creator may use, in memory, because memory is the one thing that cannot be shared out twice: a host is full when the memory its units declare they need reaches the share the system allows, and then it warns or refuses as its own setting, else the system's, says. An environment is made by a job of phases that carry their weights and their percentage (the host is chosen, the image made available, the volumes, the connector's program and the unit made, the connector waited for until it enrolls, the environment attached to it and the executors its exec node offers started, the unit looked at, and one transaction that says it runs); every command carries an identifier derived from the job, the job is held by one process at a time through a lease and taken over when that lapses, a failure or a cancel before the last phase is undone (the unit and the volumes it made are removed, the environment stands failed with the phase and the reason), and a restart of the API goes on where the last process stopped. A stopped environment is started by a job of the same kind, by a person or by the start of a turn, which says that it waits for the environment and goes on when it is up; one that is idle for as long as its setting allows is stopped; one that is unused for as long as its setting allows is scheduled for removal with a notice, and removed by a job of its own that is tried again with a pause that doubles. A directory on a person's machine follows its machine: it is attached in each session the machine has, with what its home gives it, and stands offline when the machine is away. What a host's node and an environment's connector report is applied in the transaction that moves their cursor.

What it tells people, it tells in the transaction of the event: a turn that completed or failed, a thread that is blocked, an approval that waits and a job that ended each write a row in the Inbox of the people they concern, once however often they are told, and the outbox rows of their routes that are on and want it at once, and of the destinations of the node that take the kind. The people are those who follow the thread at the level the kind takes and may view it, and, for an approval, those who can decide it and either follow the thread or asked to be told of every approval they can answer; nobody is told of what they did themselves, and a service identity is told nothing. Owning a thread, or sending an input to it, makes a person follow it. An approval that has been decided or withdrawn is marked read for everyone it asked. It is tested on a real database with a scripted machine in `tests/notifications.rs`. A machine that drops with a thread running on it tells the person it belongs to, once. Left to the parts that own the events, which call `notifications::tell` and `tell_destinations` with the people their kind has: a milestone and an announcement (the tools of the `orch` server), a request for a capability or for access and its decision, a mention in an input, a provider that is exhausted or needs attention, an environment that is stopped or falls behind, a cap, a document, and the end of a job, which `notifications::job_finished` tells once the job runner calls it.

A person's shells (`shells`) are theirs alone and live in the environment, not in a browser tab: opening one checks the gates that no permission lifts
(a setting, the environment's own switch, the local policy of a person's machine, whether the environment can be reached) and the two limits, in which a
person at the limit names the shells of their own they give up and the new one opens as those close; every way a shell ends (it exits, it is closed, its
environment stops or is made again, its opener loses what it was opened by, nobody came back to it for the time the setting gives) goes through one
function that has the machine close it, closes the row by compare-and-set, puts away the last of what it printed with the values of the environment's
secrets taken out, and writes the line of the environment's history. A shell that exits while nobody is attached is told by its machine on the
environment's stream and applied from `ingest`. It is tested on a real database through the API's requests and sockets, with a machine that keeps
shells and with a real connector process.

**A turn that failed.** The error a harness ends a turn with is kept whole on the turn: its code and sentence, what the harness or its vendor said word for word, the moment a limit of the plan ends, and whether the answer may have been cut short. A limit of the whole plan (`provider_exhausted` that is not retryable) closes the provider: it is `exhausted` with the adapter's sentence, which names the limit and when it ends, its facts take the limit with that moment, and a report from the machine that does not know of the limit does not lift it before then. A provider closed with a moment is looked at again by itself, by pre-flight when the moment has passed and by the supervisor's sweep, which also starts the threads that waited for it; one closed without a moment waits for its machine to say it is ready. A limit that covers one family of models or the spending (`provider_exhausted` that is retryable) closes nothing, since another model may answer; a credential the vendor refused puts the provider in `error`; and what passes (`provider_busy`, `provider_unreachable`) or what no adapter knows (`harness_error`) leaves the provider as it was and the thread free to try again, with the vendor's words on the turn. A thread that waits for a closed provider is blocked as `provider_exhausted` with the provider's sentence as its detail. A harness that is gone ends the turn it ran as `session_lost`. Tested in `tests/limits.rs` on a real database.

**Files of the workspace.** A snapshot of a thread's directory is a job that the runner of the engine carries out with the machine (`jobs/snapshot`, phases of the runner like every other job: a lease, a request to cancel that is read while the machine works, and a restart that goes on with the job and asks the machine again under the same command identifier); the machine's progress moves the bar forward and never back, and the last phase is the engine's own, after the point where nothing is cancelled, in which everything the list names is pinned and the snapshot is written as it came out, all in one transaction that a restart does not repeat. The list of a tree that a machine uploads when the tree changed is read, pinned and kept as the latest of its environment, and the one it replaces is let go (`manifest` reads and writes the format). The files an input carries are written into the thread's directory before its turn begins or its steer is sent (`delivery`): one `fs.materialize` for the input under the thread's `.orch` directory, asked under an identifier made of the input, the machine and the list, so that a restart goes on with the same command; the thread shows the step `files` meanwhile; a delivery of a few megabytes or of many files is a job on the runner that people can watch and stop (the turn waits for its end, and a cancelled one is a refusal like any other); and where the files cannot be written the turn starts all the same, with each file named as not delivered and why (`instructions`). A long output of a command that the timeline kept the end of is read from the store of content in pieces (`views`). Tested in `tests/delivery.rs` against a scripted machine, and the whole way through a real connector in the API's tests.

**One thread made out of another.** A switch changes what a thread with history runs on (its provider, agent profile, arrangement, environment or directory) and keeps its owners and its page; a fork gives its maker a thread of their own; a side thread is the quick fork that one request makes; several threads are switched together. `fork_plan` works out what a request would do for the caller and changes nothing: who will own the result, how the history travels (the first row of the table that the adapters accept: the session continued, forked by the harness, the harness's own archive moved to another of its kind, the turns handed over as items, a summary, or nothing) and what of it is kept, converted and dropped, the files and the agent's notes that go along, what stands still and what is left behind, how long it takes, the people on the page who could not go on, and everything that stops it (what the caller lacks, named; nothing to change; no arrangement; a model or an effort the result may not have; a provider that is not ready; a job already under way for the thread or for an environment it touches). Keeping the plan stores it for fifteen minutes; carrying it out works it out again in the same transaction, makes the job and, for a switch, takes the lock. **A lock is a job** (`locks`): the thread of an open `thread_fork` job is `blocked(switching)` as soon as no turn is running, so nothing starts, what is sent to it waits in the queue and its pending approvals are cancelled; the lock ends with the job, in any way it ends, and the queue then runs on the side the thread is on. `jobs/fork` carries a job out in the phases `lock`, `provision`, `copy`, `history`, `verify`, `commit` and `cleanup`: it waits for the running turn or interrupts it as the options say, makes what the result needs (the thread, the environment, the files by `fs.snapshot` on the source and `fs.materialize` on the target, twice, the second time for what changed meanwhile), opens the new session with the history by the first method the harness accepts and falls to the next row when it declines (`fork_history`: the harness's own archive, the items in the neutral form, or the conversation's written form, whole, left under `.orch/handoff` of the new thread's directory with a message that points at it; the text of a summary is the one thing another part fills, through `fork_history::Handoff`, and the transcript is what stands in until it does), checks the result, and commits in one transaction: the binding, the new segment and what was imported into it, the lines in the histories of both threads, the audit line and the queue. A failure or a cancel before the commit removes everything the job made and leaves the thread as it was (`Job.error.undone`); after it nothing is undone. `jobs/batch` makes one job for each plan without blockers, all locked at once, and lets `switch.batch_parallel` of them run at a time. A batch targeting a new environment creates one shared environment and provisioning job. A durable checkpoint makes retries reuse it; if its maker fails before creation, a surviving member takes over under the batch lock. Members transfer and bind independently. Only an unpublished target with no committed member or later binding is removed. `side_threads` starts a side thread on what its parent runs on, in the parent's place of the tree, with the message queued in it, limited by `thread.side_max` and `thread.side_threads`, its items kept out of the search index, begun from the parent's session forked by the harness or from its history as items, and closed by hand, by an idle day (`thread.side_idle_hours`, and the worker does it on a schedule) or by an ordinary fork that keeps it; each closing leaves one line in the parent. An environment that is made for the result is judged by what its template promises of it (the executors its exec node offers, and the harness kinds it lets run beside the tools; it is never on the machine of the provider), and judged again by what it reports when it is up. Tested with the scripted machine in `tests/forks.rs`, where a harness that keeps its sessions shows by its answers that a thread that was switched knows what was said before, by the harness's archive and by the items, and where a fork into an environment made for it writes the files chosen there and, when that fails, takes the environment away again. Not built: the page a fork would have in another topic is not compared with its source's (`ForkPlan.access.differs` is empty), and the choice of private views of a new environment is not acted on.

**Frames of a harness, and a session begun by hand.** A session is opened asking for the frames of its harness's own protocol. Each one an adapter reports is kept under the next number of its segment for as long as `diagnostics.retention_days` says, once every text in it and every name of a member has been masked with the patterns of the thread's place and the values of the secrets of its topic and of its environment, and is never kept where it cannot be masked (`raw_events`; `ingest` hands them over). A session that a person began in a harness by hand is taken in as a thread: the harness is asked for the sessions it holds, the one named is put in the environment of the caller's whose folder holds the directory it ran in, the thread's first segment names it, and the first turn opens it as an adopted session and every turn after resumes it (`adoption`, `turns`). At adoption, and only then, the harness is asked what it recorded of the session: its earlier turns, what a person said (attributed to the machine's owner) and what the agent said and did, are written into the thread once, under no turn, as items from the session before Orch that are read-only and never sent to the agent again; the thread runs on the session's own model where the harness says which and the place allows it, and otherwise a person chooses one, with the reason on the line that says the session was adopted. What adopting would do is answered before anything does (`adoption_plan`).

A ready fork also has its selected conversation before its first send. The history phase remembers
the completed-turn boundary it actually handed over; the source can continue while that happens.
`fork_history::copy_conversation` materializes independent historical segments, turns, inputs, child
lanes and requests in the existing SQL-only commit. Source ids, live leases, pending decisions, file
restore boundaries and model-input records do not become active actions in the result. Attachment
owners are pinned independently. Native-fork replay aliases are scoped to that exact new session;
converted imports and handoff files never treat a source id as a new harness id. Repeating the copy
adds neither rows nor pins. Explicit Nothing copies no conversation. A fork of adopted earlier items
does not pretend the new thread itself was adopted or offer a history retry for the source session.
The existing `tests/forks.rs` gate now reads the ready conversation and both child lanes before any
send, checks independent identity and replay, selected ranges/Nothing, the frozen boundary while the
source finishes a later turn, and the new fork's first answer. All source is subject to the integrator's proof.

What it asks of the rest of the system it asks through three small traits: `commands::Commands` (send a command to a machine, learn how it ended), `access::ResourceAccess` (may this person use this provider, this profile, this environment) and `live::LiveSink` (growing text, forwarded at once). Who may do what to a node it asks of `orch-authz` itself.

What is left to later parts, each blocking or refusing plainly and never letting a turn through unchecked: recreating, updating or moving an environment, the files an environment starts with, the mounts a directory on a machine attaches, evaluating usage caps (a turn is not started while a cap with a limit covers it, and a lease carries no allowance until caps are evaluated), the rollups of the ledger by day and month, the tools of the `orch` server, and the routes that call the functions of `inputs`, `approvals`, `views` and `binding`.

The tools of the `orch` server are answered here. A call of an agent's harness arrives as an event of its session and is checked against the thread's settings as they are at that moment (the tool must be enabled and built, the agent within `orch_tools.calls_per_minute`, the arguments what the tool's closed schema allows), done once, and answered with one command; a refusal is a result marked as an error that begins with its code and says what to do instead. `announce` tells the other threads of the agent's topic (or, where `broadcast.agent_scope` allows, of its project) by the topic's delivery, fallback and wake settings, or only the people who follow its thread; what is deferred is said first at the thread's next turn. `send_message` takes a typed chat or thread target: a chat posts to people, while a thread queues a note through its topic’s existing delivery and wake policy. Chat results say `posted`; thread results say `queued` and name the scheduled action, without claiming a harness acknowledgement. The two destinations retain their own shares, quotas and file rules. `request_capability` is decided by the capability's policy: given, refused, or asked of the people of the scope the policy names on the machine's side, never of those whose work asked; the recreation a grant leads to is queued as a job of the environments' part. The session is opened with the tools the thread enables that are built; its instructions name the tools it has, and their block on where the agent is says what its environment has and can be given. They are tested with the scripted machine (`tests/orch_tools.rs`, `tests/orch_capabilities.rs`) and, from the API's tests, against the connector as a process. The others are answered here too, over the shared tree described next, and every tool that is built is in `definitions::BUILT`, which is a list of `OrchTool::ALL` and the one place that counts them.

What was shared with an agent is its reach, and it works in it as in a file system. A live share is entries on pages whose holder is the agents of a place (`sharing`: the rows of conversations, chats and documents, each apart, on the page of the thing and for a place on its defaults page as well, changed and taken back as any entry of a page is); a copy is a row and files, written in the written form of each thing (`written`, `copies`) and kept by what is attached as `sharing::Parcels` until the thread's next turn writes them into its workspace; with nothing attached a copy is refused, not made and lost. `list_shared`, `read_shared`, `search_shared` and `download_shared` walk the tree of `tools/tree` (every name given among all the entries of a directory, a place there only for what the agent may read, a refusal that tells nothing of what is hidden), `edit_document` and the chat route of `send_message` write only where a share allows it at the moment of the call, and the one text of a conversation, a chat and a document is the same whether an agent reads it, a person exports it or it is forwarded. A place is shared with what is in it, or by itself: the first is entries on its page and on its defaults page, so that what is made inside later follows; the second is entries on its own page only, its own chat and the documents written beside it, never a conversation, since a place has none of its own. The two are told apart by the defaults page (an area that has an entry there is shared with what is in it), may both stand for the same agents, and are listed, changed and taken back each apart. Who may share is the rule of the access engine: a sharer shares up to what they hold, where the place lets holders share, and takes back what they shared. They are tested against a real PostgreSQL with the scripted machine (`tests/shared_tree.rs`, `shared_read.rs`, `shared_search.rs`, `shared_write.rs`, `shared_download.rs`, `sharing.rs`, `sharing_place.rs`) and with golden texts for the written form. Agent attachments use one workspace reader (`tools/workspace_files`) and the machine's bounded, root-confined `fs.fetch` upload before any destination transaction; ordinary chat attachment validation and pinning retain the whole file, and thread messages keep blob-backed deliveries even within one environment. `tests/shared_message_files.rs` exercises the real tools, stored bytes, references, refusal without a partial message, upload limits, changed workspaces and revoked write shares.

Direct document and chat attachment paths use `download_shared` to copy the original blob bytes, including images and retained forwarded attachments. They use the readable owner's document, node-chat or people-chat Export gate, never the thread owner's personal rights. Downloads retain their canonical filename and extension under `.orch/shared/downloads`, or use `save_to`, and ignore rendering format/detail for files. The file stream is checked against `storage.max_blob_bytes`, its complete size and content hash before workspace delivery; current owner, file/message slot, access and limit are checked again after blob I/O. The existing `Parcels` byte writer supplies equal-byte retries, no replacement of different bytes, bounded outcome admission and the original owner audit. No metadata transaction spans blob or workspace I/O. `tests/shared_attachment_download.rs` covers whole binary/empty/image/forwarded bytes and ordinal order, all three owner gates, retries/conflicts, hidden/revoked/deleted/missing data, limits, outcome budgets and deterministic changes during the blob read. Forwarded input delivery is unchanged.

Document organization is one atomic domain (`document_tree`) shared by the API and the agent tools. A real document folder contains only documents and other document folders inside an existing `docs/` area; hierarchy places and the built-in `docs`, attachment and history directories are not mutable document objects. `list_shared` exposes the nested paths and each item's current Read, Edit and Manage. `read_shared` reads document text and versions, not folders or raw attachments; folders are listed and attachment bytes use `download_shared`.

`manage_shared` takes `command: create_folder | copy | move | delete | restore` and one to twenty selected `paths`. `create_folder` takes one new folder path whose parent already exists. Copy and move require an existing writable directory in `to`; `name` optionally supplies one selected item's new basename, keeping `.md` for a text document. Parents are never implicit, existing names are never overwritten or automatically renamed, selections cannot overlap, and a folder cannot be copied or moved into itself or a descendant. One operation includes at most fifty documents and folders, counting every descendant. An inaccessible descendant refuses the whole operation without disclosing its name; no accessible prefix is changed.

Only `delete` uses preview and confirmation. Its first call changes nothing and returns the complete affected membership, revisions, file/history counts, live readers, sharing/audience facts and restoration deadlines with a random 128-bit token. Repeat exactly the selected arguments with `confirm` to soft-delete the whole selection. The token is bound to its thread and arguments, lasts for the configured management-plan lifetime (ten minutes by default), and is spent once. Membership, material, authority, grant expiry, collisions and limits are checked again in the transaction. A stale or unusable token returns `not_confirmed` without a replacement token; the agent asks again without `confirm` and reads the new complete preview. An oversized or denied plan never receives a token. Completed operation results are admitted before commit, so an insufficient answer bound changes nothing.

`create_folder`, `copy`, `move` and `restore`, including restoration of one document version, execute directly under the same applicable atomic checks. Copy reads the complete source and uses ordinary destination creation rights, ownership and access; it creates fresh folder/document/block/file identities and new history, independently pins attached bytes, remaps structured internal links across the copied selection, keeps outside references, and records provenance. Source owners, grants, shares, comments and historical versions are not cloned. The calling agent receives the normal creation Edit entry, never automatic Manage; its human owner's privileges supply no authority. Moves and restoration retain identity, content, files, owners and history. Durable actor/request receipts prevent repeated completed copies. Existing text creation and rename enter this same placement domain, and persisted legacy copy calls enter the same Copy operation; there is one public copy workflow.

`edit_document` creates or edits text inside an existing writable document directory. Use `manage_shared create_folder` for new folders and `manage_shared copy` for duplication. The adapter resolves exact typed targets on the supplied connection; all tree membership, authority, locking, namespace, material copying and durable receipts remain in the common domain. Usage caps are evaluated here. A cap covers a turn by the node on its way down, the provider, the model (the one pattern rule, which also names a group of the provider's models as `@<group>`, against the groups of the model's entry at that provider), the service tier the turn asks for (a cap that names none covers every tier, the ordinary one too), the harness kind and whom it is for (everybody, one person, a group, or the role held at the thread); of the caps counted per person that agree in everything but whom they are for, exactly one applies to a person (the one that names them, else the largest of the group and role caps, else everyone's). Pre-flight asks them under a lock for each cap that counts turns running at once: a shared cap without room blocks the thread (`quota_exceeded`, saying which), one counted per person holds only that person's input, which keeps its place while their teammates' go on, and `uncounted = block` refuses what nobody reports or what has no rate; a lease on the forwarded path carries what is left of the tightest cap that would stop it. Whenever usage is reported (no oftener than `[engine] cap_check_secs` for a thread) the turn under way is asked again, and a cap that is reached and says `stop` ends every turn it covers with the code `cap_reached`; a cap made, lowered or removed is looked at at once (`Engine::cap_changed`), and the threads that wait are looked at in the order of their oldest input whenever room may have been made. One turn is let past the caps that stand in its way by an entry of its input for each person who holds the row where each cap is defined, checked again when the turn starts and recorded (a row for each cap, a line of the audit trail and one of the thread's history); a warning and the word that a cap was reached go out once for each cap, person and period. Orch's own model calls (a summary) are counted by shared caps only and never block a turn. Tested with the scripted machine in `tests/caps.rs`, `tests/caps_models.rs` (a model, a group, the whole provider and a speed, in turns at once and in credits) and `tests/usage_rows.rs`.

Tested in `tests/model_parameters.rs`.

The port admission core is implemented independently of agent decisions: it
checks current rights and policies, coalesces canonical requests, admits reviewed
place/link/host preparation and reconciles admission separately from runtime
availability. Real request cases prove the current authority guard, distinct
port limit, requester-only close and irreversible revocation. The four tools,

Shared-content tools resolve one set of paths and identifier-tail names. An ambiguous write returns only reachable candidates before effects; a read includes one line naming its other interpretations. Search uses the common literal query grammar and entry summaries ranked as people's best matches are (the field that matched: a name or title, a description, a heading, the rest; then matching rows; then the newest), with counts and native positions, optional snippets and continuations through bounded scan windows that advance newest first. bytes under the document's current edit access and ordinary per-file and total upload limits;
an overwrite preserves the existing file identity and links. `detach` removes the named file,

detach and completed-call replay. No remote read or blob-store operation holds a SQL transaction.
