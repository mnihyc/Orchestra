# 更新与回滚

[English](../upgrades.md)

如何在一个版本上安装另一个版本，新版本无法就绪时会发生什么，如何回到旧版本，以及如何收尾断电后只做了一半的更新。源码检出中的 `scripts/smoke/` 包含部署场景。

## 更新

“管理 → 系统”显示正在运行的服务器版本、来自发布地址的最新版本（默认是本项目的 GitHub 发布页；可用 `ORCH_RELEASE_URL` 或 `[release] url` 更改）、它的说明，以及在主机上运行的准确命令。查询（包括失败的查询）共用服务器中每小时一次的缓存。查询失败时，页面会如实显示，并附上上一次成功的结果及其日期。这个页面从不运行更新程序，也拿不到 Docker 套接字，更不能写入主机的发布目录。

```sh
./update.sh v0.2.0 --from /path/to/the/release      # 文件放在一个目录里
./update.sh v0.2.0                                  # 或从发布地址获取
./update.sh latest
```

使用 `--from` 时，目录里需要有 `version.json`、前端压缩包、服务器压缩包，以及适合这台主机架构的 `orchctl` 程序，见[安装 Orch](deployment.md#1-获取发布文件)。在停止任何东西之前，更新程序会用 `version.json` 校验这些文件，以及清单中列出且存在的其他文件，然后把它们解压到正在运行的文件旁边。

如果有工作在运行，或发现不兼容的运行环境，`update.sh` 会说明这次更新要做什么，并询问是否继续（没人能回答时，`--yes` 代替回答）。最低版本号对应的预发布连接器会被报告，供检查兼容性。没有受影响的工作时，它不提问直接继续。如果读不到工作清单，它会在停止任何服务之前就停下：

```
2 environments and 1 managed provider will need an update before they work again (release v0.2.0 no longer accepts their connector).
4 threads are running. Their turns are not interrupted and their events arrive after the services are back; but if that takes longer than the 60 s that open exec tunnels wait, those tunnels are reset: the commands in them end, and the agent sees them fail.
Go on? [y/N]
```

随后更新作为一个事务运行。每一步在执行之前都先写入 `runtime/update/journal`：

1. 应用服务停止，数据库继续运行。
2. 取一份数据库转储并读回校验：`runtime/update-backups/orch-<time>-before-<tag>.dump`。
3. `server`、`frontend` 和 `cli` 换成新版本，旧的成为 `previous`。
4. 重新创建并启动服务，API 应用该版本的数据库结构变更。
5. 在 API 的容器中运行 `orchctl doctor --expect-version`，直到通过：API 应答并报告该版本，网关已连上它，worker 有心跳，节点有会话。允许 5 分钟（用 `ORCH_READY_TIMEOUT` 可更改）。

更新同时从部署包安装未修改的部署文件。修改过的配置保留，新版放在相邻的 `.new` 文件中。回滚或恢复时，更新程序也会恢复此前替换的文件。部署目录的 `.env`、`config/` 和数据不随发布文件替换。运行 `./update.sh doctor` 可随时检查内部服务和外部入口。

早于 0.1 版发布的开发构建所产生的数据库，不能作为更新的来源。版本发布后，它的迁移不再改动，之后的结构变更是新增的编号文件。不要为了让更新启动而改写已应用迁移的校验和。

### 更新机器和节点

机器上的连接器和节点程序用同样经过校验的流程自行更新。机器或节点的页面及其行内操作向管理者提供**立即更新**，它们每小时一次的自动检查遵循设置 `update.auto`。

- 服务器先暂缓新的轮次，并等所有用到这台机器的工作结束（包括节点上的每个容器），才允许安装。
- 程序替换前会校验大小和 SHA-256，替换一步完成，之后由服务管理器重启。更新会一直显示，直到新版本打招呼，或被拒绝、失败。
- 关闭自动更新时仍可在网页立即更新。网页操作和本地命令 `orch-connector update`、`orch-node update` 都不会开启自动更新。
- 低于最低版本的节点仍然能证明自己的证书。服务器先暂缓新的轮次并等它的所有容器结束，之后，对它的拒绝才附带更新许可。旧版本上的节点收不到任何会话或生命周期命令。没有共同链路协议的节点需要使用本地命令，它自己绝不判断托管的容器是否空闲。
- 托管环境和提供方的连接器保留它们自己的、经过审核的**更新**流程，该流程把镜像和连接器一起更新。

### 保留未使用的版本

系统设置**保留未使用的版本**默认是 3。更新或回滚成功后，每个部分再保留这么多个未使用的版本，最新的优先。`current` 和 `previous` 始终保留。设为 0 表示不清理，保留全部版本。读取该策略失败或策略无效时，也保留所有版本。

只有完整的部分目录才可能被清理。暂存目录、符号链接和无法识别的目录都保留。转储不会被自动清理。请把每份转储与它的清单和配套的数据块副本放在一起，见[备份与恢复](../backup-and-restore.md)。

### 更新对运行中工作的影响

| 组成 | 更新期间 | 更新之后 |
|---|---|---|
| 已连接的机器 | 会话中断，事件在本地暂存，隧道等待 60 秒的宽限 | 重新连接并发送暂存的事件。如果新版本提高了 `connector_minimum`，或它们空闲，就会自行更新 |
| 托管环境和提供方 | 继续运行，智能体程序的轮次继续，连接器暂存 | 以现状重新连接。现在装着较旧版本的容器会显示“有可用更新”。容器在更新前不会有任何变化。新版本不再接受其连接器的容器无法重新连接，会显示“需要更新” |
| 浏览器 | 套接字关闭 | 重新连接，构建变化时提示刷新 |
| 进行中的轮次 | 不会被打断 | 重新连接后收到它们的事件 |

### 新版本没有就绪时

服务停止，链接恢复原状，数据库用刚取的转储重建，旧版本启动并通过校验，`update.sh` 以错误结束并说明情况：

```
update.sh: putting release v0.1.0 back
...
all 6 checks passed
update.sh: release v0.1.0 is running again, with the database as it was before; the dump is runtime/update-backups/orch-20261011T182533Z-before-v0.2.0.dump
update.sh: release v0.2.0 did not become ready; v0.1.0 is running again as it was
```

这是场景中使用第二次结构变更无法应用的版本时的表现：它的第一次变更已经改了用户表的名字，失败之后用户表恢复原名，管理员能够登录。

## 更新智能体程序

智能体程序的版本、检查以及如何固定版本，见[智能体程序版本](../../user/agent-program-versions.md)。对更新 Orch 本身，有两点要知道：

- 一个版本可以给某个程序的清单增加测试用例。已存的检查通过了它当时全部用例的构建仍然是**已检查**，新用例显示为待运行（“已检查 · N 项检查待运行”）。在发布计划的一次查看内（每十五分钟一次；间隔为 0 表示关闭，渠道读取也一样），后台会对每个检查过的保留构建运行待运行的用例，不论它有多旧。
- 节点版本较旧的主机没有新用例。它的检查不算失败：构建仍是**已检查**，结果会写“此节点版本未运行”，直到有节点已更新的主机运行它们。请把独立节点和服务器一起更新。完全无法运行的检查（没有主机，或运行器失败）会让上一次完整检查保持原样，并说明之后的检查没有运行。版本自带固定的构建不是保留的记录：版本用自己的清单为它们认证，从安装当天起就显示**已检查**。

要使用厂商渠道之外的构建，把它复制到内部文件服务器，在**智能体程序**中登记它的 URL 和 SHA-256，然后运行**检查**。登记构建只接收这些细节，程序由节点获取。

## 回滚

```sh
./update.sh rollback --yes
```

它用同样的保护措施对调 `current` 和 `previous`，并把数据库恢复到离开要进入的那个版本时的样子，使各部分和数据库状态互相兼容。**自更新以来写入的内容会从运行中的系统丢失**，`update.sh` 会在询问之前说明这一点。

它会先保存当前数据库的一份转储（`orch-<time>-before-rollback-from-<tag>.dump`），这样再运行一次 `./update.sh rollback` 就能前进回到你离开的版本，并带着当时的内容。期间登记的机器，对恢复后的数据库来说是未知的，需要重新登记。如果内置节点是在转储之后登记的，它就是其中之一；使用了一段时间的系统早就有它了。

在停止任何服务之前，回滚会读取上一个服务器部分中的 `connectors/version.json`，检查连接器的最低版本。如果该清单缺失，或与已安装的记录不符，请先用上一个版本的发布文件恢复该部分，再重试。

## 中断之后

断电或 Ctrl-C 会让日志保持打开。更新、回滚，或遇到未完成更新的首次启动，在处理完之前都会拒绝运行：

```
update.sh: a update to v0.2.0 was interrupted (step activating); run ./update.sh recover first
```

`./update.sh status` 会说明有哪些未完成，`./update.sh recover` 把它完成或撤销：

| 停在 | `recover` 做什么 |
|---|---|
| `begin`、`staged`、`stopping`、`dumping`、`activating` | 新版本从未运行，数据库和原来一样。链接恢复，旧版本启动 |
| `restoring_entered`（回滚）、`restoring`、`restarting` | 数据库正在被替换。用离开时那份转储重建，旧版本启动 |
| `starting`、`verifying` | 新版本可能没问题。它被启动，就绪并报告其版本则保留，否则像失败的更新一样撤销 |
| `done` | 记录已关闭 |

如果停止服务或备份这类步骤失败，日志也可能保持打开，服务可能处于停止状态。先解决报告的原因，再运行 `./update.sh recover` 把上一个版本带回来。

被中断的首次启动，重复原来的 `first-start` 命令即可继续，包括 `--from` 和任何 `--restore-database` 选项。
