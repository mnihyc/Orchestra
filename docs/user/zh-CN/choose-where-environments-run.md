# 选择环境运行的位置

除非需要更强的边界，否则请不要设置**容器运行时**。这时主机的默认值适用，只要它满足模板和位置的规则。本页说明运行时是什么、创建环境时如何选择一个，以及每一种会带来什么变化。

每个环境有两个名称：它**运行于**什么之上（Docker 或一台机器），以及它的容器运行时，即把它圈住的程序。两者并排显示，例如 **Docker · gVisor**。运行时按它本来的名称显示，并用一行说明它与主机共享什么：

- **runc**：与主机共享内核。
- **gVisor**：自带的内核，用用户态写成。
- **Kata**：微虚拟机，有自己的内核。

主机额外登记的运行时（crun、Sysbox）以各自的名称显示。Docker 无法得知一个运行时是什么，所以由主机的运维人员在节点的配置里声明它。没有人声明过的运行时，视为与主机共享内核。

## 创建环境时选择运行时

1. 打开**资源 → 环境 → 添加环境**。
2. 选择模板。它给出环境起始使用的运行时。
3. 打开**容器运行时**。它列出所选主机提供的运行时。模板不允许、或位置禁止的运行时会连同原因一起显示。如果位置要求使用某一种运行时，它就是你唯一能选的。
4. 如果你是专家，**其他容器运行时名称…**接受主机已登记的名称。

模板在**限制 → 容器运行时**下写出它的默认运行时，并且可以限制选择。位置的策略可以允许、禁止或要求某些运行时，并且可以像任何策略一样被锁定。Orch 在创建容器之前会再次检查策略，所以改变了的规则可以中止正在进行的创建或替换。同一运行时已登记的别名遵循同样的规则。

环境页面会显示这一对名称、说明它共享什么的那一行，以及**此处的限制**：在它的运行时之下哪些方面的工作方式不同，以应当怎么做和原因的形式写出。同样的几行会在每个会话开始时告诉智能体，并在环境移动或它的运行时改变之后再告诉一次。

如果主机在拉取或构建镜像时空间用完了，请在那台主机上释放空间后重试。磁盘满了绝不会让 Orch 改用较旧的缓存镜像。

## 有哪些组合

| 运行于 ＼ 运行时 | 无 | runc | gVisor | Kata |
|---|---|---|---|---|
| **机器** | 唯一的选择 | — | — | — |
| **Docker** | — | 默认 | 已登记 `runsc` 时 | 已登记 Kata 且存在 `/dev/kvm` 时（虚拟机上要嵌套虚拟化） |

## 每种组合支持什么

| | 机器 | runc | gVisor | Kata |
|---|---|---|---|---|
| 边界 | 无 | 共享内核 | 用户态内核 | 自己的内核 |
| 工作区、主目录、状态 | 目录 | 卷 | 卷 | 卷（virtio-fs） |
| 终端、文件、MCP 服务器、执行器、浏览器、端口 | ✓ | ✓ | ✓ | ✓ |
| 共享和只读挂载 | ✓ 就地 | ✓ | ✓ | ✓（virtio-fs，元数据较慢） |
| 在外部做出更改时的文件事件 | ✓ | ✓ | 重新扫描（约 1 秒） | 重新扫描（约 1 秒） |
| 不创建新容器就更改挂载或设备 | ✓ | ✓ | 环境会被重新创建 | 环境会被重新创建 |
| 受限网络 | — | ✓ | ✓ 在主机上已证明可用时 | ✓ 在主机上已证明可用时 |
| 主机网络 | ✓ | 需要能力 | ✗ | ✗ |
| 内置 Docker | ✓ 自己的 | ✗（只能通过特权容器和 Docker 套接字的关键能力） | ✓ Docker 自己的网络没有防火墙：请用 `--network=host` 运行你在里面启动的容器来访问网络（`-p` 仍然提供端口） | ✓ |
| `sudo` 和其他以其所有者身份运行的程序 | ✓ | ✓ | 仅当 `runsc` 以 `--allow-suid` 登记时（可选脚本 `gvisor.sh` 会这样做） | ✓ |
| 内部的虚拟机（QEMU） | ✓ KVM | ✓ 带 `kvm` 能力的 KVM | 仅软件仿真 | 仅软件仿真 |
| GPU | ✓ | 需要能力 | ✗ | ✗ |
| 安装在卷之外的软件在停止、空闲停止、回收和重启之后仍然保留 | ✓ | ✓ | 仅当使用 `--overlay2=none`（由可选的 `gvisor.sh` 设置） | ✓ |
| 用同一镜像替换时，该软件作为保留层保留 | ✓ | ✓ | 仅当使用 `--overlay2=none` | ✓ |
| 主机在容器限制之外多花的内存 | 无 | 无 | 数十 MiB | 约 0.3 GiB |
| 主机的设置 | 无 | 无 | 安装并登记 `runsc` | 安装并登记 Kata；KVM |

某种组合无法具备的能力，会显示在它本来会被提供的位置，并带有原因。例如，Kata 下不提供**主机网络**，因为客户机有它自己的网络。

## 安装的软件何时丢失

你用 `apt` 或手动安装在卷之外的软件，位于容器的文件系统里。**停止**、**空闲停止**、**回收**和**重启**在表里写明的地方会保留它。容器会在这些情况下被**替换**：**重建**、更新、更改模板、更改无法实时应用的配置或能力（gVisor 或 Kata 下对挂载或设备的每一次更改，以及**内置 Docker** 本身）、替换失败的容器，以及移动。

用同一镜像替换时，在运行时允许的地方，软件会作为保留层保留。换了镜像则从头开始。方案和授权对话框会说明适用哪一种：“环境创建之后、安装在卷之外的软件（例如用 apt 安装的）会被移除。镜像自带的内容和卷会保留。”卷（包括 `/var/lib/docker`）始终保留。

当移动和恢复方案无法从旧的托管容器带走保留的镜像时，会显示这个警告。带走镜像的方案会保留软件，即使它测得的大小为零。从机器的某个目录移动，不会移除安装在那台机器上的软件。

在 gVisor 的默认覆盖层下，环境每次停止，软件都会丢失：“你安装在卷之外的软件会在环境每次停止时丢失；请把它放在镜像或卷里。”可选的脚本 `deploy/hosts/runtimes/gvisor.sh` 会以 `--overlay2=none` 登记 `runsc`，这样就和 runc 一样保留它。见运维页面“推荐的主机设置”。

## 内置 Docker 与开发者工具模板

**内置 Docker**是一项能力。只有在有自己内核的运行时（Kata、gVisor）之下才会提供它，在那里它的风险是中等的：它给出所有内核能力并移除容器的过滤器，仅限于客户机内部。Docker 把它的数据保存在 `/var/lib/docker`。Orch 在环境每次启动时，把它变成环境状态卷的一个挂载：在 Kata 下是卷的一个文件里自己的文件系统，在 gVisor 下是它的一个目录。在与主机共享内核的情况下，只有通过主机的套接字或特权模式才可能使用 Docker。两者都是关键的，默认被拒绝。

请先申请内置 Docker，再安装 Docker。授予它会重新创建环境。

- **开发者工具**模板用一个内置了 Docker Engine（带 buildx 和 compose）、x86_64 和 aarch64 的 QEMU，以及常用构建工具的镜像创建。在那里用 `orch-dockerd` 启动 Docker。
- 在**默认**环境里，智能体可以用 `sudo apt-get install docker.io` 自己安装 Docker，并启动 `dockerd`。
- 没有 Docker 的镜像会在申请内置 Docker 的地方这样说明：“此镜像中没有安装 Docker：请用 sudo 安装它（它会保留到环境被重新创建），或者用内置它的开发者工具创建环境。”

如果里面的服务在本地能响应，但它发布的端口从另一台机器无法访问，请检查内部 Docker 的网桥子网是否与主机或客户端的网络重叠。请在环境里的 `/etc/docker/daemon.json` 中选择一个不重叠的 `bip`，并重启内部的守护进程。如果启动失败，请阅读 `/var/log/dockerd.log`。辅助程序最多等待一分钟，只有在启动进程退出时才会重试一次。

Orch 会在主机上可用的镜像里查找 Docker 客户端、Docker 守护进程和两个 QEMU 系统程序，无论这个镜像是拉取的、构建的、导入的还是已缓存的。这检查的是哪些程序存在，并不会启动它们。如果镜像无法检查，可用性保持未知；检查失败并不表示缺少程序。

Kata 或 gVisor 环境里的虚拟机通过软件仿真运行，可以工作但很慢。在普通容器上，`kvm` 能力让它们变快，代价是容器因持有主机的 `/dev/kvm` 而隔离较弱。
