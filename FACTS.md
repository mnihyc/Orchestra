# Background completion and agent continuation

Reviewed 2026-11-06 against source `14fe63d0f6be49d73109d8c2cbdd5fb88826c9c7`. This is a facts and implementation-impact report. No application code, supported-capability declaration or specification was changed.

Claude Code documents native follow-up turns after background completion. Codex terminal completion reports an event without starting a model turn. Codex **subagent messages have a separate, experimental wake option**, disabled by default in both versions examined. Source-based implication: Orch currently requires its own admitted turn and cannot safely restore wake behavior by changing a launch flag alone.

## Evidence and version boundaries

- [The release manifest](deploy/harness-builds.json) pins Claude Code **2.1.312** and Codex **0.165.0**; **0.166.0 is a comparison version**, not another current manifest default.
- An isolated, network-disabled image reported Claude Code 2.1.312. Its binary SHA-256 matches the manifest. Its `--help` was captured. The same image reported Codex 0.165.0 and generated `app-server generate-json-schema --experimental`.
- Official Codex source was read at immutable release commits: [0.165.0, 360319d8](https://github.com/openai/codex/tree/360319d8dee62d87e2d59fc0c21805d79519cfed) and [0.166.0, 6ff1e1ca](https://github.com/openai/codex/tree/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856). The terminal watcher and child-completion sender are identical in those versions. The command, collaboration and subagent-activity item variants examined are also identical; this is not a claim that the whole protocols match.
- Claude's linked official pages are current documentation, not archived 2.1.312 documentation. Explicitly documented introduction versions help establish applicability, but do not replace an exact-build observation. No native agent session, model request, build or test was run for this report.

## Claude Code

The relevant invocation is `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages`, with `--forward-subagent-text` for child messages. The pinned help confirms these flags. Help describes the latter as “Forward subagent text and thinking blocks as assistant/user messages with parent_tool_use_id set”.

## Orch today

These are source findings and retained acceptance boundaries, not newly reproduced defects.

1. **Normal turn end does not unconditionally close the session.** The engine terminalizes the turn, settles items and approvals, closes its lease, clears its active pointer and wakes preflight. Preflight chooses another eligible input or idles. The relevant code is [turn end](crates/control/engine/src/turns.rs#L233), [input selection](crates/control/engine/src/preflight.rs#L475), and [turn creation with an input id](crates/control/engine/src/preflight.rs#L1527). Native session lifetime, model-authorization lifetime and the foreground state are different.
2. **Claude already keeps its native-tools process while the session stays open.** Its default 300-second idle exit applies only when it uses an external executor; zero disables that timer. However, the next native-tools turn deliberately restarts the process to reload directory instructions. Settings changes and explicit close can also restart it. Keeping idle sessions alone therefore does not establish retained work across later user turns. See [timer](extensions/agents/claude-code/src/conversation.rs#L367), [next-turn restart](extensions/agents/claude-code/src/conversation.rs#L594), and [quiet shutdown](extensions/agents/claude-code/src/conversation.rs#L975).
3. **Codex also refreshes before later turns.** The engine's session-reload rule reopens an in-environment session; the adapter unsubscribes and waits for native close before resume when replacing a loaded lane. With a zero unload delay, that is a potential task-ending boundary, not a reason to turn the delay up globally. See [engine reload decision](crates/control/engine/src/turns.rs#L692), [unload before resume](extensions/agents/codex/src/runtime.rs#L253), and [session close](extensions/agents/codex/src/lib.rs#L1431).
4. **Claude managed background-disable is deliberate.** `ProfileConfig.background_tasks` defaults false. Managed launch then forces background tasks and several other autonomous features off after applying profile variables. The shared `managed_environment` is also used by managed settings and provider probes. `SendMessage`, `ListAgents`, workflow, monitor and scheduling tools have separate exclusions. Removing all these restrictions would be a broader change than restoring owned background tasks. See [profile](extensions/agents/claude-code/src/config.rs#L111), [managed settings/environment](extensions/agents/claude-code/src/sessions.rs#L534), [environment application](extensions/agents/claude-code/src/sessions.rs#L686), and [tool exclusions](extensions/agents/claude-code/src/tools.rs#L732).
5. **Neither mapper admits unsolicited foreground turns.** Claude starts an Orch turn only from its explicit start command; its mapper falls back to the last turn for late task items, while a further result without an active turn is ignored. Codex records a native turn without a pending Orch start as foreign and suppresses its events. Simply enabling native wake risks work outside normal ownership, display and accounting. See [Claude start](extensions/agents/claude-code/src/conversation.rs#L594), [last-turn mapping](extensions/agents/claude-code/src/events.rs#L698), [result handling](extensions/agents/claude-code/src/events.rs#L2321), [Codex foreign turn](extensions/agents/codex/src/events.rs#L989), and [engine turn matching](crates/control/engine/src/ingest.rs#L1072).
6. **Current management is command-specific.** Codex declares native background List/End; Claude declares it unavailable. The engine captures an ephemeral existing-session roster, projects it for each current reader, and checks Interact plus exact generation/item ownership for End. None of that is a completion-triggered input producer. The stored command timeline can outlive a turn; the live roster itself is not durable. See [background capture/projection](crates/control/engine/src/background.rs#L173), [End job](crates/control/engine/src/jobs/background_end.rs), and both adapter descriptors.
7. **The header already has two distinct presentations.** A native-command count/list remains beside Idle where available; subagent chips open child lanes. The chips have no End control or wake-setting explanation. Codex's current collaboration mapper sets subagent `name` and `role` to null even though upstream thread/activity metadata can supply labels. See [header](frontend/src/features/thread/Header.tsx#L348), [command list](frontend/src/features/running/Running.tsx), [subagent chips](frontend/src/features/timeline/SubagentChips.tsx), and [Codex projection](extensions/agents/codex/src/events.rs#L2279).
8. **Runtime retention needs an explicit audit.** Provider idle-stop reads busy turns/leases and sign-in state; it does not test the returned session count in that decision. Background-only activity is not a turn or open lease by definition. Environment idle-stop and native instruction/skill/MCP refresh are additional lifetime boundaries. This is an implementation-impact observation, not a newly qualified failure. See [provider idle decision](crates/control/engine/src/provider_runtime.rs#L1121), [busy facts](crates/control/db/src/queries/resources.rs#L6148), and [environment reaper](crates/control/engine/src/reaper.rs#L225).
9. **Stop preserves ownership and uncertainty.** Existing Stop ends only commands started by the stopped turn, leaves earlier intentional work alone and holds pending inputs. A forced controller end retains the session and waits for confirmed native idle; it is not proof of a process exit. Completion wake must preserve those boundaries. See [forced end](crates/control/engine/src/turns.rs#L2484), [native-busy guard](crates/control/engine/src/background.rs#L703), and [Codex command ownership](extensions/agents/codex/src/runtime.rs#L994).

The retained QA position is narrower than native task support: Codex command roster/exact End is supported; Claude has task/event/stop primitives, while full owned command List/End integration remains unproved. Historical frontend presentation receipts establish neither a safe continuation path nor current native-world acceptance. Unsupported End controls stay absent.

## What Orch would have to change

| Area | Required consequence of completion-triggered continuation |
| --- | --- |
| Session lifetime | Retain the exact session/generation while owned tasks or subagents run, through idle, another user turn and normal instruction/skill/MCP refresh. Coordinate runtime idle-stop, switch/fork/archive/cleanup and recovery. Keep existing configuration refresh semantics by deferring or safely applying refresh; do not silently retain stale instructions. A process restart does not restore live work. |
| Turn start without fresh human input | Add a completion-origin admission path through existing preflight and turn storage, linked to the actual initiating input/run. Handle native synthetic turns before model execution, not only after receiving their output. Claude's automatic follow-ups and Codex's optional message wakes need the same admission authority. An ordinary terminal end may instead require Orch to request the continuation. |
| Authority and ongoing background inference | Retain each origin's author, accepted credential/scope, model/provider bounds and original task identity. Recheck Interact and model Use before continuation; hold when lost as approved. Recheck accepted/current credential and account bounds at future acts. A continuing child can use a model while the foreground is idle, so its inference also needs valid authorization; closing the foreground lease cannot leave it unowned. Task output supplies information, never new permission. |
| Accounting | Give the admitted continuation its own turn, request/lease attribution and actual usage, charged to the originating author. Account for child use after foreground completion without reopening or double-counting the completed turn. Coalesced vendor completions from different inputs/authors cannot silently become one authority. |
| Stop and exact End | Preserve current Stop queue holds and earlier-turn command survival. Define how pending/future completion wakes participate in a hold. Keep exact End a native control operation with a factual outcome, not a new model instruction; suppress any control-induced native follow-up until its policy is decided. Reused ids, stale generations, late/duplicate completion and unknown cleanup cannot revive work. |
| Timeline and live state | Record an admitted wake cause tied to the task's starting item/run before rendering model output. Keep a current named list of both command tasks and subagents while idle; distinguish a command finishing from the model starting. Capture lifecycle events independently of whether any viewer has an ephemeral roster watch open. |
| Setting and capabilities | Use the existing settings machinery for the approved option, default on. Resolve it before native launch and continuation admission; show it beside the wake notice. Distinguish the configured preference from effective availability for the installed build/arrangement. Native feature defaults, personal profile overrides, observer support and verified End support must not create hidden wake paths. |

These changes cross shared adapter contracts/events, the two adapters, session supervision, preflight/leases/accounting, background projection/controls and the existing thread header/timeline/settings consumers. No endpoint-specific authorization path or second task process manager is required by these facts.

## What the thread must show

The approved presentation requires **advance visibility**, not a retrospective notification alone. While idle, the thread lists all known background tasks and subagents **by name**, gives each a supported End control, says it will wake when they finish, and places the setting beside that statement. A woken turn is labelled **`Woken by: <task> finished`**. Nothing may wake the thread without its ability to do so having been visible beforehand.

Publish that eligibility in shared thread state before admitting the continuation, so it can be rendered for every authorized reader. This introduces no requirement for a person to watch the thread or acknowledge each wake.

| Thread element | Claude facts available | Codex facts available | Missing wiring or limitation |
| --- | --- | --- | --- |
| Name and kind of work still running | Task `description`, `task_type`, optional `subagent_type`, Agent input name/description and Bash command/description. Live-set snapshots reconcile missed individual events. | Terminal command text; subagent child id and `agentPath`; optional thread name/nickname/role. | A description or command is a useful label, not a guaranteed friendly name. Use reported labels and a clearly identified fallback. Codex currently discards available child name metadata. Claude's live-set snapshot is not wired into Orch. |
| Current state while the main agent is Idle | Per-task updates and completion status, plus the full background set. `run_id` distinguishes a resumed run; `parent_task_id` can group nested work when reported. | Terminal roster membership and command-item status; child `agentsStates` and activity/child-turn events. | Idle does not mean no work. Do not turn offline, unsupported, a truncated list or a missed snapshot into zero. Neither upstream reports Orch's current authorization hold. |
| End beside each supported task or subagent | Native SDK `stopTask` is a candidate mechanism for either kind; Orch's complete owned List/End capability is still false. | Exact terminal terminate is already integrated. Child-turn interruption/agent controls are a separate surface; a terminal `processId` cannot end a subagent. | Advertise only verified controls for that kind/build. Existing subagent chips have no End path. Ending a parent session to stop one child would also affect other work. Keep unsupported controls absent and say when native control is unavailable. |
| “Will wake when these finish” and nearby setting | Native synthetic follow-up behavior and task origins make the promise technically plausible. | Terminal completion needs a controller wake; child completion can use the optional native message-wake path only after admission is integrated. | This text must describe the effective setting and exact eligible live set. With wake off, unsupported, stopped, held or unknown, show the actual condition instead. Neither harness supplies this Orch setting or promise. |
| `Woken by: <task> finished` at the resulting turn | Correlate task/run id, completion notification and `origin.runId` where supplied. | Correlate original command item/process identity, or child activity/thread identity, with the newly admitted continuation. | Persist the causal link and reader-safe label before output. Do not derive it from assistant prose or a final result alone. If several completions are combined, name the actual set; failed or stopped work must not be labelled successfully finished. |
| No invisible future wake | Lifecycle starts and live snapshots expose known work before it completes. | Command start items and child spawn/activity items expose eligible work. | The controller must publish the eligible set/setting before allowing the wake, including a very short task, reconnect and a thread with no viewer currently connected. Native automatic wake has no built-in acknowledgment that Orch has published that state. An unattributed event cannot be allowed to create a hidden turn. |

This extends the existing command list and child lanes; it does not require promoting the ephemeral roster into a permanent process inventory. Durable origin, outcome and wake-cause records can remain distinct from live observations.

## Questions left open

- **Integrator decision:** which exact-pin mechanism gates a native synthetic turn before any model use, particularly Claude subscription sessions with no per-request forwarder? No documented host-approval handshake for every background wake was established here.
- Will Codex child wakes use its experimental feature or an Orch-admitted continuation, and how will effective native configuration be constrained to prevent an unadvertised second wake path?
- Does turning the option off only suppress wake, or also prevent new background launches; what happens to already-running tasks?
- Does a later Stop hold all remaining wakes from earlier inputs, or only those already pending? Earlier tasks must retain their current survival semantics.
- Which terminal outcomes trigger continuation: successful completion only, failure too, and never an explicit End without a separate decision?
- How are simultaneous completions from different originating authors admitted when the native CLI combines notifications into one model turn?
- How will task retention coexist with current next-turn instruction/skill/MCP reload, model changes, external-executor arrangements and provider/environment idle-stop?
- Can exact-pin Claude roster/stop ownership and Codex child End be proven sufficiently to offer those controls, while preserving truthful partial availability?

## Qualification still required

The current regression tests cover retained items, exact command ownership, source/run correlation and Stop holds. They do **not** establish the new wake contract. Exact selectors and environment prerequisites accompany the private handoff notes.

Central native qualification must use a scripted provider and isolated homes, with no real model credentials:

1. On Claude 2.1.312, launch one background Bash and one background Agent, return a foreground result, keep stream-json input open and send no second prompt. Capture actual task/roster frames and every subsequent model request/result. Repeat after input EOF and orderly termination/resume; distinguish resumed history from live work.
2. On each Codex pin, observe terminal completion after the foreground turn ends without another `turn/start`; then exercise child completion with message-wake disabled and enabled, including native Stop. Source behavior is not substituted for the resulting wire trace.
3. Before enabling Orch's option, prove admission occurs before every automatic model request; revoke the origin's Interact/model Use/key authority during background work and verify the required hold. Account for child use while idle and for duplicate/coalesced completion exactly once.
4. Prove idle and next-turn retention, End/Stop races, reconnect/session generation changes, no-viewer completion capture, and the named list/setting/wake label at desktop and phone sizes. No model output may precede its wake label or originate from an eligible set that was never shown.
