# 更新 Orch 和机器

机器或节点比较正在运行的版本与自己的 Orch 服务器推荐构建。有新推荐时列表标记可用
更新，页面显示两者版本。下载完不表示已经运行，只有新进程重新连接才改变运行版本。

## 机器和节点

机器管理者或节点的主机管理者可在页面或行动菜单选择立即更新。Orch 暂停新轮次，等待
使用该机器的所有活动轮次结束；节点包含所有受管单元。程序从自己的服务器下载，验证
大小和 SHA-256，再原子替换可执行文件，由服务管理器启动。此过程不中断已有轮次。

等待、下载、安装和重连时显示更新中，新进程报告版本后清除。拒绝或失败保留原因，
损坏下载保留原程序。包括自动更新在内的请求均被审计。

物理连接器和节点在 `update.auto` 允许时每小时检查推荐构建，使用相同的等待、验证和
安装。环境或提供方内部连接器不自行替换。

## 本机策略拒绝时

机器主人有最终决定权。本地 `update.auto = false` 拒绝网页请求，提示该键及本地命令：

```sh
orch-connector update
orch-node update
```

只运行本机对应程序的命令。这是显式本地同意，允许在自动更新关闭时安装已验证构建，
不改保存的设置。离线机器先重连才能收命令。低于服务器最低接受版本时，更新后才能
恢复普通工作；节点在等待全部受管轮次结束后，可在普通连接被拒绝时取得更新。
不会因节点自己没有程序会话就推断单元空闲。协议不再兼容时，由运维在主机运行节点更新。

## 环境和提供方运行时

环境沿用自己的更新流程。预检列出镜像、连接器、其他待变更及阻止替换的运行工作，
管理者检查方案后启动作业。更新主机节点不会暗中替换单元镜像或连接器。
提供方运行时同样通过自身更新或下次启动取得连接器。目录连接器属于物理机器，遵循本机策略。

## 服务器

管理 → 系统显示运行版本、从运维发布地址读取的最新版本、说明链接和在服务器主机执行
的完整命令，例如：

```sh
./update.sh v1.2.3
```

默认地址为本仓库 GitHub 发布。运维可用 `config/orch.toml` 的 `[release] url` 或
`ORCH_RELEASE_URL` 指定兼容来源。成功和失败读取都至少缓存一小时。
`release.check_days` 控制定时通知，打开系统页使用同一小时缓存。失败时保留原因及
上一次成功、有日期的结果。

服务器没有网页自更新按钮；这需要主机文件或 Docker 套接字权限。运维在主机运行
事务式 `update.sh`，验证发布、备份数据库，新服务未就绪则回滚。升级恢复指南说明备份和回滚。

API 更新数据库时网页入口仍可用。已打开页面显示迁移、完成步骤、数据库能报告的行数和
耗时，之后重新连接。API 更新日志也打印这些步骤，不能报告的计数保持未知。
